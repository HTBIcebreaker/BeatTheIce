# 작업계획서

## 작업자

`2인분` (담당 기능: P2P QR 프로필 교환)

## 작업명

90분 프로토타입 — P2P QR 프로필 교환 (`features/p2p-qr`, Supabase 연동 기준)

## 근거 문서

- `memory/기획 개요.md` — 플로우 A: P2P 만남과 프로필 교환 (최상위 SOT). ⚠️ 12장은 90분 프로토타입 기준 "서버·DB 사용 안 함(mock + localStorage)"으로 유지되어 있음 — 공용 문서는 수정하지 않는다.
- `memory/기능 정의서.md` 14장 "90분 프로토타입 4인 분담안" 중 **2인분: P2P QR 프로필 교환**
- `memory/기술계획서.md` — 공용 기준 문서. 문서상으로는 mock adapter(`mock.ts`) + `BroadcastChannel` 기준이지만, 이 폴더(`memory/p2p-qr/`)에서는 실제 Supabase 접속 정보(`.env.local`)와 `supabase/schema.sql`이 이미 존재하는 저장소 상태에 맞춰 **Supabase 직접 연동**으로 진행한다. 이 차이는 공용 문서를 고치지 않고 이 문서에만 기록한다.
- `supabase/schema.sql` — `profiles`, `party_members` 테이블과 RLS 정책

## 변경 이력

- 최초 작성 시에는 90분 프로토타입 기본 규칙(로컬 mock + Context + localStorage)을 기준으로 계획했다.
- 실제 Supabase 프로젝트 스키마(`supabase/schema.sql`)와 `.env.local` 접속 정보가 이미 존재함을 확인해, mock adapter가 아니라 **처음부터 실제 Supabase 쿼리로 구현**하는 방향으로 계획을 갱신했다.
- 이 갱신 근거로 공용 문서(`기획 개요.md`, `기술계획서.md`)를 함께 고쳤으나, 공용 문서는 다른 담당자가 관리하는 영역이라는 피드백을 받아 **원래 내용으로 되돌아갔다(타인이 되돌림)**. 이후로는 공용 문서를 수정하지 않고, Supabase 사용이라는 이 폴더만의 결정과 근거를 이 문서에만 남긴다.

## 목표

다른 세 담당자의 작업 완료를 기다리지 않고, `features/p2p-qr` 폴더 안에서 실제 Supabase(`profiles`, `party_members`) 쿼리로 QR 표시부터 상대 프로필 확인까지의 흐름을 독립적으로 완성한다.

## 범위

- 내 프로필 QR 표시
- QR 스캔 모달 또는 스캔 성공 대체 동작(카메라 연동이 지연되면 "스캔 성공" 버튼 폴백)
- 상대방 프로필 카드 구현
- 스캔 전 · 성공 · 재스캔 상태 구현

## 결정 사항

- **QR 스캔 이력 저장 여부: 저장하지 않는다(파티 중에만 임시 공개).**
  - 근거: `supabase/schema.sql`에 스캔 이력을 남길 테이블이 없어 저장하려면 공용 스키마 변경(새 테이블 + RLS)이 필요하지만 이는 팀 합의 대상이지 이 폴더에서 단독 결정할 사안이 아니다. 기능 정의서 PROF-03 완료 기준도 이력 없이 반복 스캔만 요구한다.
  - 영향: `resolveProfile`은 매번 `profiles`/`party_members`를 조회만 하고 별도 insert를 하지 않는다. 재스캔 시 이전 상대 정보를 새 정보로 교체만 하면 된다.
  - 이 결정은 `memory/기획 개요.md` 11장 미결정 사항 목록에도 반영했다(사용자 요청).

## 데이터/쿼리 개요

- 내 QR 값: 로그인(Anonymous Auth) 후 확보한 `profiles.id`(uuid)를 그대로 QR 문자열로 사용한다.
- 상대 프로필 조회(`resolveProfile`): `supabase.from('profiles').select('*').eq('id', qrValue).single()`
- 같은 파티 소속 검증: `party_members`에서 `party_id = 현재파티` AND `profile_id = 스캔된id` 행이 있는지 확인한다. `profiles` 테이블의 RLS는 `authenticated`에게 전체 조회를 허용하므로(파티 무관), **같은 파티인지 여부는 애플리케이션 코드에서 직접 검증**해야 한다.
- 자기 QR 스캔, 존재하지 않는 프로필, 다른 파티 소속은 모두 이 애플리케이션 레벨 검증에서 걸러 안내 메시지를 띄운다.

## 계획

1. `src/contracts`(`types.ts`, `adapters.ts`, `events.ts`)가 동결되어 있는지 확인한다. 아직 없으면 `Profile`, `PartyMember` 타입과 `QrPort` 인터페이스만 최소로 로컬에 정의하고, 공용 계약 파일 신설이 필요한 부분은 `ALPHA-TODO(owner: p2p-qr, consumer: shell-profile)`로 남긴다.
2. `src/features/p2p-qr/{components, adapter.ts, fixtures.ts, index.ts}` 구조를 생성한다. `fixtures.ts`는 UI 골격을 먼저 그릴 때만 임시로 쓰고, 곧바로 실제 쿼리로 교체한다.
3. `adapter.ts`에 `createSupabaseBrowserClient()`를 사용하는 실제 `QrPort` 구현체를 작성한다(`getMyQrValue`, `resolveProfile`).
4. `qrcode.react`로 내 QR 표시 컴포넌트를 구현한다.
5. QR 스캔 진입 UI를 구현한다: 1차로 `html5-qrcode` 연동을 시도하고, 세션 내 즉시 안정화되지 않으면 "스캔 성공" 버튼으로 지정한 상대 `profiles.id`를 조회하는 폴백을 기본값으로 둔다.
6. 상대방 프로필 카드 컴포넌트를 스캔 전 / 스캔 성공 / 재스캔 세 가지 상태로 구현한다.
7. `party_members` 조회로 같은 파티 소속 여부를 검증하는 로직을 `adapter.ts`에 넣고, 다른 파티/자기 QR/존재하지 않는 QR 예외를 처리한다.
8. 다른 기능 폴더를 import하지 않고, 자기 폴더의 실제 Supabase 쿼리만으로 렌더링·조작되는지 확인한다.
9. `profile:changed`(상대 프로필 갱신 반영)는 Supabase Realtime 구독으로 재현하되, 공통 Context 연결은 `ALPHA-TODO`로 남긴다.
10. `QR 열기 → 상대 QR 인식(또는 스캔 성공 버튼) → 상대 프로필 확인 → 다른 사람 스캔` 흐름을 실제 Supabase 데이터로 자체 점검한다.
11. `feat/qr` 브랜치에 최소 1회 커밋하고, 다른 1차 작업 브랜치와는 병합하지 않는다. `supabase/schema.sql` 변경이 필요하다고 판단되면 직접 고치지 않고 전원 합의 후 알파 담당자에게 넘긴다.

## 완료 기준

- `QR 열기 → 상대 QR 인식 → 상대 프로필 확인 → 다른 사람 스캔` 흐름을 실제 Supabase 데이터로 시연할 수 있다.
- 다른 담당자의 기능 폴더를 직접 import하지 않는다.
- 공통 계약(`Profile`, `QrPort`)의 타입과 시그니처를 준수한다.
- 다른 사람 재스캔 시 기존 상대 정보가 새 정보로 교체된다.
- 카메라 권한 거부, 다른 파티 QR, 자기 QR 스캔 등 예외 케이스가 최소 UI 안내로 처리된다.
- 같은 파티 소속 검증이 애플리케이션 코드에서 이루어진다(`profiles` RLS만으로는 파티 경계가 강제되지 않음을 인지한 상태).
- 미연결 지점(Realtime 구독의 공통 Context 연결 등)은 모두 `ALPHA-TODO`로 기록되어 있다.
