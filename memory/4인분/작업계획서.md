# 4인분 작업계획서

## 1. 작업 정보

- 담당: `4인분`
- 기능: 롤링 페이퍼·Supabase adapter·모바일 마감·알파 통합
- 작업 브랜치: `feat/rolling-integration`
- 1차 소유 디렉터리: `src/features/rolling-paper/**`
- 작업 기준: `memory/기획 개요.md` → `memory/기능 정의서.md` → `memory/기술계획서.md`

## 2. 목표

90분 프로토타입에서 롤링 페이퍼를 다른 기능과 독립적으로 작성·조작할 수 있는 기능 조각으로 완성한다. 1차 기능 완료 후에는 알파 통합에서 네 담당자의 결과를 연결하고, 모바일 화면의 일관성과 3분 발표 시나리오를 검증한다.

## 3. 범위

### 1차 독립 구현

- 수신자 선택
- 롤링 페이퍼 메시지 입력
- 작성자 공개·익명 선택
- 메시지 작성 완료 피드백
- 받은 메시지 목록과 빈 상태
- mock adapter를 이용한 작성 즉시 목록 반영
- Supabase 환경변수·UUID 사용 시 `rolling_messages` 테이블과 수신함 RPC 연결
- Supabase 연결 전에도 시연할 수 있는 `localStorage` 폴백
- 모바일 너비에서 단독으로 시연 가능한 레이아웃

### 알파 통합

- `ALPHA-TODO`로 남겨둔 공유 상태·내비게이션 연결 수집
- mock adapter를 `DemoContext` 기반 adapter로 교체
- `rolling:created` 이벤트 연결
- 네 기능 브랜치의 병합과 소유자별 충돌 해결 지원
- 공통 색상, 간격, 버튼, 팝업의 모바일 UI 마감
- 데모 초기 상태와 전체 E2E 시나리오 검증

## 4. 제외 범위

- `src/features/shell-profile/**`, `src/features/p2p-qr/**`, `src/features/mission/**` 내부 수정
- 1차 구현 중 `src/app/page.*`, 전역 CSS, Context, `src/contracts/**` 수정
- Supabase 외의 신규 백엔드·DB·인증 제공자 추가
- 롤링 페이퍼와 무관한 신규 기능
- 알파 시작 후 신규 기능 추가나 대규모 리팩터링

## 5. 예정 파일

```text
src/features/rolling-paper/
├─ components/
│  ├─ RollingPaperFeature.jsx
│  ├─ RollingPaperComposer.jsx
│  └─ RollingPaperList.jsx
├─ adapter.js
├─ adapter.test.js
├─ mock.js
└─ index.js
```

기존 프로젝트가 JavaScript를 사용하므로 팀의 공통 계약에서 다르게 정하지 않는 한 `.js`/`.jsx`를 사용한다. 예정 파일명은 공통 계약 동결 결과에 따라 바뀐 수 있다.

## 6. 데이터·adapter 계약

```ts
type RollingMessage = {
  id: string
  partyId: string
  senderId: string | null
  senderName: string
  receiverId: string
  receiverName: string
  body: string
  isAnonymous: boolean
  createdAt: string
}

type RollingPaperPort = {
  listReceived(profileId: string): RollingMessage[]
  createMessage(message: RollingMessage): void
}
```

- 1차에는 `mock.js`의 fixture와 `localStorage` adapter로 독립 시연을 보장한다.
- 인증된 UUID 프로필과 파티 ID가 있으면 Supabase adapter를 사용한다.
- `createMessage`가 성공하면 같은 기능 내의 목록에 즉시 반영한다.
- 알파 통합 전에는 다른 기능의 Context나 데이터를 직접 import하지 않는다.
- 공통 계약에 익명 여부가 없다면 1차 mock 내부에서만 관리하고 `ALPHA-TODO: contract-change`를 남긴다.

## 7. 구현 순서

1. `main`을 `git pull --ff-only`로 최신화한다.
2. `feat/rolling-integration` 브랜치를 최신 `main`에서 생성한다.
3. 공통 타입, adapter, 이벤트 계약을 확인하고 1차 작업 중 동결한다.
4. mock 참가자·롤링 페이퍼 메시지와 localStorage·Supabase adapter를 구현한다.
5. 작성 폼과 수신 목록을 구현한다.
6. 필수값·자기 자신 수신·글자 수 제한의 최소 검증을 추가한다.
7. 모바일 너비와 빈 상태를 확인하고 독립 happy path를 검증한다.
8. 미연결 지점을 `ALPHA-TODO`로 기록하고 1차 커밋을 생성한다.
9. 팀의 1차 브랜치가 모두 준비되면 `alpha/integration`에서 병합·연결·E2E를 수행한다.
10. 검증 결과와 후속 이슈를 `memory/4인분/작업 내역서.md`에 기록한다.

- [x] 공개·익명 선택이 작성 결과에 반영된다.
- [x] 빈 메시지, 자기 자신 수신, 글자 수 초과가 차단된다.
- [x] 작성 완료 후 목록에 즉시 반영된다.
- [x] 받은 메시지가 없을 때 빈 상태가 표시된다.
- [x] 익명 메시지에 작성자 식별 정보가 노출되지 않는다.
- [x] 파티 종료 전에는 받은 메시지가 잠겨 있다.
- [x] Supabase 수신함 RPC가 익명 발신자 ID를 `null`로 반환한다.
- [x] 모바일 너비에서 가로 스크롤이 생기지 않는다.
- [x] `src/features/rolling-paper` 밖의 기능 내부를 직접 import하지 않는다.
- [ ] 모든 미연결 지점에 유효한 `ALPHA-TODO`가 있다.
- [ ] 알파 통합 후 롤링 페이퍼가 E2E 마지막 단계에서 작성·열람된다.
- [x] 프로덕션 빌드가 성공한다.

## 10. 폴백과 리스크

| 리스크 | 대응 | 폴백 |
| --- | --- | --- |
| 공통 계약에 익명·수신자 필드 부족 | 공통 파일을 즉시 수정하지 않고 `ALPHA-TODO` 기록 | 1차는 mock adapter의 확장 필드 사용 |
| 다른 기능 지연 | 독립 mock 시연을 먼저 완료 | 알파에서 고정 프로필·미션 상태로 연결 |
| 통합 충돌 | 충돌 파일의 원 소유자가 해결 | 기능 삭제 대신 adapter 폴백 유지 |
| 화면 마감 시간 부족 | 시연 흐름에 필요한 화면만 정리 | 기능별 기존 스타일 유지 |
| 롤링 페이퍼 공개 시점 연동 지연 | 알파에서 파티 상태와 연결 | 데모 내비게이션으로 종료 후 장면 재현 |
| Supabase 환경변수·인증 미설정 | UUID 기반 실데이터 adapter를 준비 | localStorage adapter로 자동 전환 |

## 11. 완료 기준

- `features/rolling-paper` 기능이 mock adapter만으로 독립 실행된다.
- 작성·익명·목록·빈 상태의 happy path와 필수 예외가 동작한다.
- 다른 담당자의 소유 디렉터리를 수정하지 않는다.
- 알파 통합 후 `P2P 프로필 교환 → 사진 미션 → 결과·보상 → 롤링 페이퍼`가 중단 없이 시연된다.
- 모바일 UI, 데모 초기화와 프로덕션 빌드가 검증된다.
- 결과와 미해결 이슈가 `memory/4인분/작업 내역서.md`에 기록된다.
