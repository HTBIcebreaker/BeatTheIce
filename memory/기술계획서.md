# BeatTheIce 90분 프로토타입 기술계획서

## 1. 목적

4명이 90분 동안 BeatTheIce의 핵심 가치를 시연할 수 있는 모바일 웹 프로토타입을 완성하기 위한 기술 범위와 작업 규칙을 정의한다.

본 문서는 운영 서비스용 아키텍처가 아니라 발표 가능한 데모 구현을 기준으로 한다. 제품 범위는 `memory/기획 개요.md`, 세부 동작은 `memory/기능 정의서.md`를 따른다.

## 2. 기술 의사결정

### 확정 구조

- 프레임워크: Next.js App Router
- 언어: JavaScript 또는 TypeScript 중 프로젝트 생성 시 하나로 통일
- UI: Tailwind CSS
- 아이콘: Lucide React
- 애니메이션: 필수 장면에만 Framer Motion 사용
- QR 생성: `qrcode.react`
- QR 인식: 실제 카메라 연동이 즉시 되면 `html5-qrcode`, 지연되면 데모 스캔 버튼으로 대체
- 상태 관리: React Context
- 새로고침 보존: `localStorage`
- 탭 간 데모 동기화: 브라우저 `BroadcastChannel`

### 사용하지 않는 것

- 별도 Express 또는 Socket.IO 서버
- Supabase, Firebase 등 외부 백엔드
- 데이터베이스와 ORM
- 실제 인증·인가
- 이미지 업로드 서버
- 결제 및 쿠폰 API
- 별도 프론트엔드·백엔드 저장소

## 3. 런타임 구조

```text
Next.js App
├─ App Router pages
├─ Client Components
├─ Demo Context
├─ mock data
├─ localStorage
└─ BroadcastChannel
```

모든 핵심 기능은 브라우저에서 동작한다. 서버 저장이 필요한 기능은 구현하지 않으며, 발표 도중 필요한 상태만 브라우저에 유지한다.

## 4. 화면 경로

| 경로 | 역할 | 목적 |
| --- | --- | --- |
| `/` | 공통 | 데모 시작 및 HOST/GUEST 역할 선택 |
| `/party` | GUEST | MAIN, 내 프로필, QR 스캔, 상대 프로필 |
| `/mission` | GUEST | 현재 미션 확인 및 텍스트 제출 |
| `/host` | HOST | 일반·미션·결과 메시지 발행과 상태 전환 |
| `/rolling-paper` | 공통 | 롤링 페이퍼 작성 및 메시지 확인 |

라우트가 늦어지면 `/party` 한 화면에서 모달로 기능을 전환한다. 시연 완성도가 라우트 분리보다 우선한다.

## 5. 최소 데이터 모델

```ts
type Role = 'HOST' | 'GUEST'
type MessageType = 'GENERAL' | 'MISSION' | 'RESULT'

type Profile = {
  id: string
  name: string
  mbti: string
  intro: string
  imageUrl: string
}

type HostMessage = {
  type: MessageType
  title: string
  body: string
}

type Mission = {
  id: string
  title: string
  description: string
  reward: string
  status: 'IDLE' | 'ACTIVE' | 'SUBMITTED' | 'RESULT'
  submission?: string
}

type RollingMessage = {
  id: string
  from: string
  to: string
  body: string
}

type DemoState = {
  role: Role
  myProfile: Profile
  scannedProfile?: Profile
  hostMessage?: HostMessage
  mission: Mission
  rollingMessages: RollingMessage[]
}
```

필드는 시연에 사용하는 것만 유지한다. 작성 시각, 서버 ID, 권한, 감사 로그 등 운영용 필드는 추가하지 않는다.

## 6. 상태 관리 규칙

### React Context

`DemoProvider`가 역할, 프로필, 상대 프로필, 호스트 메시지, 미션과 롤링 페이퍼 상태를 제공한다.

최소 액션은 다음과 같다.

- `switchRole(role)`
- `scanProfile(profileId)`
- `publishMessage(message)`
- `publishMission(mission)`
- `submitMission(text)`
- `announceResult(reward)`
- `addRollingMessage(message)`
- `resetDemo()`

### localStorage

- 키는 `beattheice-demo-state` 하나만 사용한다.
- 상태가 바뀔 때 저장하고 앱 시작 시 복원한다.
- 발표 직전 `resetDemo()`로 고정된 초기 상태를 복원한다.

### BroadcastChannel

- 채널명은 `beattheice-demo`로 고정한다.
- HOST 탭의 메시지·미션·결과 변경을 GUEST 탭에 전달한다.
- 지원되지 않거나 통합이 지연되면 한 화면의 역할 전환으로 시연한다.
- 탭 간 동기화는 보조 기능이며 필수 완료 조건이 아니다.

## 8. 4인 파일 소유권

동일 파일 충돌을 줄이기 위해 개발 시작 전에 파일 소유권을 고정한다.

| 담당 | 소유 범위 | 금지 사항 |
| --- | --- | --- |
| 1인 | `app`, `MobileShell`, `MyProfileCard`, 공통 내비게이션 | 다른 담당 컴포넌트 내부 수정 금지 |
| 2인 | QR 관련 컴포넌트, `PartnerProfileCard` | Context 구조 임의 변경 금지 |
| 3인 | HOST, 팝업, 미션 관련 화면·컴포넌트 | 공통 스타일 전면 수정 금지 |
| 4인 | 롤링 페이퍼, demo 데이터, 통합 스타일 | 통합 전 기능 삭제 금지 |

`DemoContext`, 공통 타입과 전역 CSS는 0~10분에 함께 확정한 뒤 한 명만 수정한다.

## 9. Git 작업 규칙

- 브랜치: `feat/profile`, `feat/qr`, `feat/mission`, `feat/rolling-integration`
- 커밋은 담당 기능 단위로 최소 1회 생성한다.
- 통합 담당자는 55분부터 `main` 또는 통합 브랜치로 순서대로 병합한다.
- 충돌 발생 시 공통 골격 담당자와 통합 담당자가 즉시 결정한다.
- 75분 이후에는 신규 기능을 추가하지 않고 오류만 수정한다.

## 10. 90분 실행 계획

| 시간 | 작업 |
| --- | --- |
| 0~10분 | Next.js 골격, Context 타입, demo 데이터, 파일 소유권 확정 |
| 10~55분 | 4명이 담당 화면을 병렬 구현 |
| 55~65분 | 프로필·QR 기능 통합 |
| 65~75분 | HOST·미션·롤링 페이퍼 통합 |
| 75~85분 | 모바일 UI, 상태 초기화, 치명적 오류 수정 |

## 11. 기능별 폴백

| 목표 기능 | 1차 구현 | 실패 시 폴백 |
| --- | --- | --- |
| QR 인식 | 실제 카메라 스캔 | `스캔 성공` 버튼으로 샘플 프로필 표시 |
| 실시간 미션 | BroadcastChannel 탭 동기화 | 한 화면 역할 전환으로 상태 확인 |
| 프로필 사진 | 로컬 정적 이미지 | 이니셜 아바타 |
| 상태 보존 | localStorage | 메모리 상태만 사용 |
| 페이지 전환 | App Router | 단일 화면 모달 전환 |

폴백 적용은 실패가 아니라 90분 내 시연 완성을 위한 계획된 결정이다.

## 12. 검증 체크리스트

- [ ] `npm install` 후 추가 환경 변수 없이 실행된다.
- [ ] 모바일 너비에서 가로 스크롤이 생기지 않는다.
- [ ] GUEST 프로필과 QR이 표시된다.
- [ ] 스캔 동작 후 상대 프로필이 표시된다.
- [ ] HOST가 일반·미션·결과 메시지를 전환할 수 있다.
- [ ] GUEST가 미션을 확인하고 텍스트를 제출할 수 있다.
- [ ] 미션 결과와 보상이 표시된다.
- [ ] 롤링 페이퍼를 작성하고 확인할 수 있다.
- [ ] 데모 초기화가 동작한다.
- [ ] 발표 시나리오가 3분 이내에 끝난다.

## 13. 완료 정의

빌드 성공만으로 완료로 보지 않는다. 한 명이 모바일 화면을 조작해 `P2P 프로필 교환`과 `실시간 미션 수행`을 순서대로 시연할 수 있고, 롤링 페이퍼까지 보여줄 수 있을 때 프로토타입이 완료된 것으로 판단한다.
