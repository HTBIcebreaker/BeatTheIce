# BeatTheIce 90분 프로토타입 기술계획서

## 1. 목적

4명이 90분 동안 BeatTheIce의 핵심 가치를 시연할 수 있는 모바일 웹 프로토타입을 완성하기 위한 기술 범위와 작업 규칙을 정의한다.

본 문서는 운영 서비스용 아키텍처가 아니라 발표 가능한 데모 구현을 기준으로 한다. 제품 범위는 `memory/기획 개요.md`, 세부 동작은 `memory/기능 정의서.md`를 따른다.

## 2. 기술 의사결정

### 확정 구조

- 프레임워크: Next.js App Router
- 언어: JavaScript 또는 TypeScript 중 프로젝트 생성 시 하나로 통일
- UI: Tailwind CSS
- 아이콘: Lucide React
- 애니메이션: 필수 장면에만 Framer Motion 사용
- QR 생성: `qrcode.react`
- QR 인식: 실제 카메라 연동이 즉시 되면 `html5-qrcode`, 지연되면 데모 스캔 버튼으로 대체
- 사진 미션: `<input type="file" accept="image/*" capture="environment">`로 촬영·선택하고 Canvas에서 최대 1280px, JPEG 품질 0.72로 압축
- 상태 관리: React Context
- 새로고침 보존: `localStorage`
- 탭 간 데모 동기화: 브라우저 `BroadcastChannel`

### 사용하지 않는 것

- 별도 Express 또는 Socket.IO 서버
- Supabase, Firebase 등 외부 백엔드
- 데이터베이스와 ORM
- 실제 인증·인가
- 이미지 업로드 서버
- 결제 및 쿠폰 API
- 별도 프론트엔드·백엔드 저장소

## 3. 런타임 구조

```text
Next.js App
├─ App Router pages
├─ Client Components
├─ Demo Context
├─ mock data
├─ localStorage
└─ BroadcastChannel
```

모든 핵심 기능은 브라우저에서 동작한다. 서버 저장이 필요한 기능은 구현하지 않으며, 발표 도중 필요한 상태만 브라우저에 유지한다. 사진 미션은 네트워크 전송 없이 압축된 Data URL로 저장해 같은 출처의 HOST 탭 또는 역할 전환 화면에서 확인한다.

## 4. 화면 경로

| 경로 | 역할 | 목적 |
| --- | --- | --- |
| `/` | 공통 | 데모 시작 및 HOST/GUEST 역할 선택 |
| `/party` | GUEST | MAIN, 내 프로필, QR 스캔, 상대 프로필 |
| `/mission` | GUEST | 현재 미션 확인 및 텍스트·사진 제출 |
| `/host` | HOST | 일반·미션·결과 메시지 발행과 상태 전환 |
| `/rolling-paper` | 공통 | 롤링 페이퍼 작성 및 메시지 확인 |

라우트가 늦어지면 `/party` 한 화면에서 모달로 기능을 전환한다. 시연 완성도가 라우트 분리보다 우선한다.

## 5. 최소 데이터 모델

```ts
type Role = 'HOST' | 'GUEST'
type MessageType = 'GENERAL' | 'MISSION' | 'RESULT'
type SubmissionType = 'TEXT' | 'PHOTO'

type Profile = {
  id: string
  name: string
  mbti: string
  intro: string
  imageUrl: string
}

type HostMessage = {
  type: MessageType
  title: string
  body: string
}

type MissionSubmission = {
  type: SubmissionType
  text?: string
  imageDataUrl?: string
  fileName?: string
}

type Mission = {
  id: string
  title: string
  description: string
  reward: string
  submissionType: SubmissionType
  status: 'IDLE' | 'ACTIVE' | 'SUBMITTED' | 'RESULT'
  submission?: MissionSubmission
}

type RollingMessage = {
  id: string
  from: string
  to: string
  body: string
}

type DemoState = {
  role: Role
  myProfile: Profile
  scannedProfile?: Profile
  hostMessage?: HostMessage
  mission: Mission
  rollingMessages: RollingMessage[]
}
```

필드는 시연에 사용하는 것만 유지한다. 작성 시각, 서버 ID, 권한, 감사 로그 등 운영용 필드는 추가하지 않는다.

## 6. 상태 관리 규칙

### React Context

`DemoProvider`가 역할, 프로필, 상대 프로필, 호스트 메시지, 미션과 롤링 페이퍼 상태를 제공한다.

최소 액션은 다음과 같다.

- `switchRole(role)`
- `scanProfile(profileId)`
- `publishMessage(message)`
- `publishMission(mission)`
- `submitMission(submission: MissionSubmission)`
- `announceResult(reward)`
- `addRollingMessage(message)`
- `resetDemo()`

### localStorage

- 키는 `beattheice-demo-state` 하나만 사용한다.
- 상태가 바뀔 때 저장하고 앱 시작 시 복원한다.
- 사진은 압축 후에만 Data URL로 저장하며, 저장 실패 시 현재 메모리의 미리보기를 유지하고 재촬영을 안내한다.
- 발표 직전 `resetDemo()`로 고정된 초기 상태를 복원한다.

### BroadcastChannel

- 채널명은 `beattheice-demo`로 고정한다.
- HOST 탭의 메시지·미션·결과 변경과 GUEST 탭의 텍스트·사진 제출을 양방향으로 전달한다.
- 지원되지 않거나 통합이 지연되면 한 화면의 역할 전환으로 시연한다.
- 탭 간 동기화는 보조 기능이며 필수 완료 조건이 아니다.

│  │  ├─ adapter.ts
│  │  ├─ mock.ts
│  │  └─ index.ts
│  ├─ p2p-qr/                   # 2인 전용
│  │  ├─ components/
│  │  ├─ adapter.ts
│  │  ├─ mock.ts
│  │  └─ index.ts
│  ├─ mission/                  # 3인 전용
│  │  ├─ components/            # HOST, 미션, 사진 제출·확인
│  │  ├─ adapter.ts
│  │  ├─ mock.ts
│  │  └─ index.ts

│     ├─ components/

│     ├─ mock.ts

기존 저장소의 React 컴포넌트와 스타일은 재사용할 수 있으나, 90분 동안 대규모 리팩터링은 하지 않는다. 각 기능은 자기 폴더 밖의 내부 파일을 직접 import하지 않고 `index.ts`에 공개된 항목만 사용한다.

## 8. 4인 독립 작업 분리

1차 구현에서는 네 명 모두 독립적으로 실행 가능한 기능 조각을 만든다. 다른 담당자의 기능 완료를 기다리거나 다른 담당자의 브랜치를 먼저 병합해서는 안 된다.

| 담당 | 소유 디렉터리 | 독립 산출물 | mock 입력 |
| --- | --- | --- | --- |
| 1인 | `features/shell-profile` | 모바일 Shell, 역할 전환, 내 프로필 | HOST/GUEST 샘플 프로필 |
| 2인 | `features/p2p-qr` | QR 표시, 스캔 상태, 상대 프로필 | QR 문자열과 상대 프로필 fixture |
| 3인 | `features/mission` | HOST 메시지, 텍스트·사진 미션 제출·확인, 결과·보상 | 미션, 압축 샘플 이미지와 제출 상태 fixture |
| 4인 | `features/rolling-paper` | 롤링 페이퍼 작성·목록 | 참가자와 메시지 fixture |

### 1차 작업 완료 조건

- 담당 기능이 자기 폴더의 mock만으로 렌더링되고 조작된다.
- 다른 기능 폴더를 직접 import하지 않는다.
- 공통 계약에 정의된 타입과 adapter 시그니처를 준수한다.
- 실제 Context나 다른 기능이 없어도 happy path를 시연할 수 있다.
- 미연결 지점에는 임시 구현을 넣고 `ALPHA-TODO` 주석을 남긴다.

### 공통 파일 규칙

- `contracts`는 첫 10분에 네 명이 합의한 뒤 동결한다.
- 1차 작업 중 `app/page`, 전역 CSS, Context는 지정된 공통 담당자 한 명만 수정한다.
- 계약 변경이 필요해도 즉시 공통 파일을 바꾸지 않고 `ALPHA-TODO: contract-change`로 기록한다.
- 다른 담당자의 소유 디렉터리 수정은 금지한다.

## 9. 기능 간 인터페이스 계약

각 기능은 구현체가 아니라 adapter 인터페이스에 의존한다. 1차 작업에서는 mock adapter를 주입하고, 알파 통합에서 실제 공유 상태 adapter로 교체한다.

```ts
type ProfilePort = {
  getCurrentProfile(): Profile
  switchRole(role: Role): void
}

type QrPort = {
  getMyQrValue(): string
  resolveProfile(qrValue: string): Promise<Profile>
}

type MissionPort = {
  getCurrentMission(): Mission
  publishMission(mission: Mission): void
  submitMission(submission: MissionSubmission): void
  announceResult(reward: string): void
}

type RollingPaperPort = {
  listReceived(profileId: string): RollingMessage[]
  createMessage(message: RollingMessage): void
}
```

### 이벤트 계약

| 이벤트 | 발행 기능 | 소비 기능 | 최소 payload |
| --- | --- | --- | --- |
| `profile:changed` | shell-profile | p2p-qr | `Profile` |
| `qr:scanned` | p2p-qr | shell-profile | `{ profile: Profile }` |
| `mission:published` | mission | shell-profile | `Mission` |
| `mission:submitted` | mission | mission | `{ missionId, submission: MissionSubmission }` |
| `mission:result` | mission | shell-profile | `{ missionId, reward }` |
| `rolling:created` | rolling-paper | rolling-paper | `RollingMessage` |

1차 작업에서는 각 기능 내부 mock event bus로 이벤트를 재현한다. `BroadcastChannel`이나 공유 Context 연결은 알파 통합 작업으로 미룬다.

### `ALPHA-TODO` 작성 형식

```ts
// ALPHA-TODO(owner: mission, consumer: shell-profile)
// mission:published 이벤트를 실제 공유 event bus에 연결
// fallback: MOCK_ACTIVE_MISSION을 사용 중
```

모든 임시 연결에는 담당 기능, 소비 기능, 필요한 연결, 현재 폴백을 기록한다. 알파 사이클 시작 시 `rg "ALPHA-TODO" src` 결과를 통합 백로그로 사용한다.

## 10. Git 작업 규칙

- 브랜치: `feat/profile`, `feat/qr`, `feat/mission`, `feat/rolling-integration`
- 커밋은 담당 기능 단위로 최소 1회 생성한다.
- 1차 작업 브랜치끼리는 서로 merge하지 않는다.
- 각 브랜치는 자기 기능의 mock 실행 상태로 커밋한다.
- 1차 작업 완료 후 `alpha/integration` 브랜치를 생성해 네 브랜치를 병합한다.
- 충돌은 기능 담당자가 자기 소유 파일을, 알파 담당자가 공통 파일을 해결한다.
- 알파 사이클에서는 신규 기능을 추가하지 않고 연결·E2E·치명적 오류만 처리한다.

## 11. 90분 실행 계획

| 시간 | 작업 |
| --- | --- |
| 0~10분 | 공통 계약, feature 폴더, 파일 소유권 동결 |
| 10~55분 | 4명이 mock 기반 기능을 완전히 병렬 구현 |
| 55~60분 | 각 브랜치 독립 동작 확인 및 `ALPHA-TODO` 수집 |
| 60~75분 | 알파 통합 사이클: 네 브랜치 병합 및 adapter 연결 |
| 75~85분 | E2E 한 사이클, 모바일 UI, 치명적 오류 수정 |
| 85~90분 | 발표 시나리오 리허설 및 데모 상태 초기화 |

## 12. 알파 통합 및 E2E 사이클

알파 작업은 1차 기능 개발과 분리된 두 번째 작업 사이클이다. 1차 기능의 범위를 늘리지 않고 필연적으로 겹치는 부분만 연결하고 검증한다.

### 알파 입력

- 독립 완료된 4개 기능 브랜치
- `rg "ALPHA-TODO" src`로 수집한 연결 목록
- 동결된 공통 타입, adapter와 이벤트 계약
- 각 기능의 mock fixture와 happy path

### 알파 작업 순서

1. `alpha/integration` 브랜치를 최신 기준 브랜치에서 생성한다.
2. 네 기능 브랜치를 순서대로 병합한다.
3. 기능별 mock adapter를 공유 `DemoContext` adapter로 교체한다.
4. 이벤트 계약을 Context 또는 `BroadcastChannel`에 연결한다.
5. 라우트, 전역 레이아웃과 내비게이션을 한 번만 조립한다.
6. 모든 `ALPHA-TODO`를 해결, 연기 또는 폴백 유지로 분류한다.
7. 아래 E2E 시나리오를 한 사이클 실행한다.

### E2E 검증 시나리오

`GUEST 역할 선택 → 내 프로필·QR 확인 → 상대 QR 스캔 → 상대 프로필 확인 → HOST 사진 미션 발행 → GUEST 미션 확인·촬영·미리보기·제출 → HOST 인증 사진 확인·결과 발표 → GUEST 보상 확인 → 롤링 페이퍼 작성·열람`

### 알파 완료 기준

- 위 E2E 시나리오가 중단 없이 한 번 완주된다.
- 기능 간 데이터 타입 오류와 import 오류가 없다.
- `ALPHA-TODO`가 모두 처리 상태와 담당자를 가진다.
- 미해결 연동은 발표를 막지 않는 폴백으로 유지된다.
- 프로덕션 빌드가 성공한다.
- 알파에서는 디자인 개선보다 흐름 연결과 시연 안정성을 우선한다.

### 알파 이슈 기록 형식

| ID | 연결 구간 | 증상 | 임시 폴백 | 담당 | 상태 |
| --- | --- | --- | --- | --- | --- |
| `ALPHA-001` | QR → 프로필 | 예시 | 샘플 프로필 | 2인 | OPEN |

병렬 개발 중 발견한 교차 기능 문제는 즉시 해결하려고 작업을 멈추지 않는다. 위 형식으로 기록한 뒤 알파 사이클에서 처리한다.

## 13. 기능별 폴백

| 목표 기능 | 1차 구현 | 실패 시 폴백 |
| --- | --- | --- |
| QR 인식 | 실제 카메라 스캔 | `스캔 성공` 버튼으로 샘플 프로필 표시 |
| 사진 미션 | 후면 카메라 촬영·압축·미리보기 | 앨범 선택, 마지막으로 샘플 인증 이미지 사용 |
| 실시간 미션 | BroadcastChannel 탭 동기화 | 한 화면 역할 전환으로 상태 확인 |
| 프로필 사진 | 로컬 정적 이미지 | 이니셜 아바타 |
| 상태 보존 | localStorage | 메모리 상태만 사용 |
| 페이지 전환 | App Router | 단일 화면 모달 전환 |

폴백 적용은 실패가 아니라 90분 내 시연 완성을 위한 계획된 결정이다.

## 15. 완료 정의

빌드 성공만으로 완료로 보지 않는다. 1차로 네 기능이 각자의 mock adapter를 사용해 독립 완료되고, 2차 알파 작업에서 한 명이 모바일 화면을 조작해 `P2P 프로필 교환`과 `사진 인증을 포함한 실시간 미션 수행`을 순서대로 시연하며 롤링 페이퍼까지 보여줄 수 있을 때 프로토타입이 완료된 것으로 판단한다.
